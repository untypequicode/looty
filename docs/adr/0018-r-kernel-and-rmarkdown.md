# R runs in the browser (WebR) or on the project's Jupyter server; R Markdown converts to notebooks

Issue #237 asks for R cells next to Python. ADR 0003 and 0008 already decided that Looty executes no code on its own server and that the browser engine is Pyodide (Python).

Decision:
- **R runs through the project's Jupyter server** (IRkernel, chosen as the notebook's kernel) **or in the browser with WebR** (see the update below). The language of a notebook is read from its `kernelspec` / `language_info`; Looty adds nothing new on the backend. Running an R notebook with Pyodide is refused with an explicit message.
- ~~WebR is not shipped for now~~: first decision, reversed by the WebR update below.
- **R Markdown / Quarto documents are converted, not run**: `.Rmd` and `.qmd` convert to and from `.ipynb` in the browser (`editor/rmarkdown.ts`), jupytext-style. The exact chunk header, fence length, blank lines, line endings and YAML delimiters are kept in `metadata.looty.rmd`, so a round trip gives back the same text. Outputs and Markdown attachments are not written to `.Rmd` / `.qmd`.
- Chunk options are interpreted only for rendering exports (`echo`, `include`, `results`, Quarto `#|` lines); execution ignores them.

Consequences: no new server endpoint, no stored secret. The RStudio-like panels (environment, plots, help, console) are not built yet; they need silent kernel requests outside cells.

Update (issue #239): the RStudio-like panels now exist (`components/notebook/RPanels.vue`, `editor/rPanels.ts`). They use **kernel queries outside cells**: an `execute_request` with `store_history: false` (no execution number, no cell), whose output goes back to the panel by its `parent_header` and is never written to the notebook. Environment and help queries are silent: they do not start a kernel, and are skipped if it is not connected. The console runs with history on the same kernel. Plot history is read from the cells' outputs and the console's, not from the kernel. The R code sent is fixed text; names typed by people are always quoted as R strings. Not covered: the panels need the Jupyter engine (not Pyodide), variables are listed from the global environment only, and a long calculation delays the answer (requests queue behind it, 15 to 20 s then an explicit timeout).

Update (WebR, issue #237): **R now runs in the browser with WebR**, as a third engine next to Pyodide and Jupyter, so R needs zero setup. The Engine dialog offers "R (navigateur)"; the choice is saved in the notebook like the others (`metadata.looty.engine = "webr"`, `kernelspec` `ir`, language R, so the file still opens in JupyterLab). It replaces the earlier choice to leave WebR out: the payload is real but loaded only when needed, and the Jupyter relay needed a server and an IRkernel that most people do not have. R Markdown / Quarto documents opened as notebooks now default to this engine.
- **Engine abstraction**: `composables/useWebrKernel.ts` has the same surface as `useNotebookKernel` (Pyodide): `state`, `message`, `run`, `restart`, `start`, `complete`, plus `query` for the R panels. The editor picks the active kernel by engine, so cells, Run all, exports and the Rmd flow are unchanged. The logic that does not need WebR (harness, output parsing, plots, completion, package list) is in `editor/webrEngine.ts` and tested with a fake WebR.
- **One WebR per person**, started on the first R run of an open notebook (never at page load): variables survive between cells, outputs are shared through the notebook like Pyodide. Cells go through a small R harness that evaluates expression by expression, prints visible values, writes data frames as HTML tables (first 100 rows), reports errors with a call stack, and echoes warnings to stderr. Plots use WebR's canvas device: the bitmaps become PNG outputs. SVG is not produced.
- **Project files and packages**: project files (not `.ipynb`, up to 5 MB each, 25 MB total) are copied to R's working directory before each run, like Pyodide. Packages are installed only on an explicit gesture (`install.packages()`, shimmed to `webr::install()`, or `webr::install()` itself) from the public WebR repository `repo.r-wasm.org`; a project can list packages in `r-packages.txt` (one per line) to install them at kernel start. Unlike `requirements.txt`, nothing writes to that file automatically.
- **R panels** (#239) work with WebR: the same fixed R code is sent through `query`, silent requests do not start WebR, and the console runs with graphics like a cell. Environment, help and console are the same as with Jupyter. Requests queue behind a running calculation (explicit timeout), as before.
- **Interrupt**: the PostMessage channel cannot interrupt a computation (that needs SharedArrayBuffer), so "Restart R" terminates the worker and the session is lost. Accepted: it keeps Looty free of cross-origin isolation headers.
- **Payload and self-hosting**: the npm package `webr` (0.6.1, R 4.6) is a dependency; its `dist/` (R.wasm about 18 MB, R.js, the lazily loaded base library images, `webr-worker.js`) is served as static assets under `/webr/` from the application (Nitro public assets, cached one day), like `/pyodide/`. About 30 MB are downloaded the first time R runs (shown to the person in the loading message), the browser keeps them; the Docker image grows by about 48 MB and the `webr` loader chunk (about 60 kB) is imported dynamically, so nothing is fetched by pages that never run R. No call to a CDN is made to start R, so self-hosted, offline and strict-CSP instances work. The only third-party request is the explicit package download from `repo.r-wasm.org`. Looty ships no Content-Security-Policy itself; an instance that adds one needs `worker-src 'self'`, `script-src 'self' 'wasm-unsafe-eval'` and, for package installs, `connect-src https://repo.r-wasm.org`.
- **Static serving trap**: WebR lazy-loads library images named `*.data.gz` and decompresses them itself. Nitro serves a `.gz` file with `Content-Encoding: gzip`, so the browser decompressed them first and WebR failed on the first plot. The `/webr/**` route rule sets `content-encoding: identity` (Nitro does not override a header already set).
- **Channel**: WebR runs with the PostMessage channel, not SharedArrayBuffer or the service worker channel, so no `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` header is needed site-wide (they would break the embeds and OAuth pop-ups). The Looty service worker (push only) is not involved.

Gaps: no interrupt, no SVG, packages not built for WebAssembly are unavailable (the Jupyter engine covers them), `r-packages.txt` is manual, completion covers base R and loaded packages only, and the memory ceiling is the browser's.

PC tunnel: a project can also reach a Jupyter on a person's own computer through an outgoing connection, see ADR 0020.
