# The install generator runs in the browser; secrets never touch the site

The official site offers a generator for a self-hosted install (reverse proxy, domain, instance name, login method). It could be a service on the site's server that builds and stores the files, then serves them to a `curl` command. That would make the site a single point of failure for every install and would put other people's secrets (database password, `LOOTY_SECRET_KEY`, OIDC secret) on our server.

Decision: **the generator is a static page, with no call to the site's server**. It offers two outputs:
- a **zip** (compose file, `.env`, Caddyfile or Traefik labels, README) built in the browser, with secrets generated by WebCrypto;
- a **command** `curl -fsSL https://looty.untypequicode.fr/install.sh | sh -s -- --domain … --proxy caddy|traefik --name … --auth …` carrying **only non-secret parameters**. `install.sh` generates the secrets on the target machine (`openssl rand`) and writes the same files as the zip.

Why: the site only serves static files (it can be mirrored, or the script read from GitHub), nobody's secrets cross the network or end up in shell history, and the zip and the command produce identical files from the same templates.

Consequences: the templates are shared by the page and `install.sh` and must be tested together in CI (both outputs give byte-identical files apart from the secrets). An OIDC client secret entered in the generator only goes into the zip; for the command, `install.sh` asks for it interactively.
