# AI agents are read-only by default and write only through a per-page, expiring grant

People want to ask a model about their pages and have it draft or fix text. The risks are obvious: a model (or an instruction hidden in a page it reads) that rewrites documents nobody pointed it at, reaches pages the person cannot see, or leaks an API key. We considered a global "allow editing" switch, a per-connection permission, and trusting the system prompt; none of them survives a prompt injection, and the first two are too coarse (one page the user wants help on, a whole workspace exposed).

Decision: **a conversation is read-only until the person grants it write access to one exact page, with a mode and an expiry**, and the server enforces everything with the rights of the person, never with what the prompt says.

- `ai_connections` hold the provider (`openai`, `anthropic`, `gemini`, `perplexity`, `openai_compatible` for Ollama and similar), model, optional base URL and the API key **encrypted with `crypto.rs`**. The API never returns the key, only whether there is one and its last four characters. Base URLs follow the CalDAV rules (https and public addresses, unless `CALDAV_ALLOW_PRIVATE` or `AI_ALLOW_PRIVATE` is `true`, which a local Ollama needs).
- Tools offered to the model: `list_pages` and `read_page` (only what `visible_pages` / `require_page_read` give the person, across workspaces including their personal space), and `write_page`.
- `ai_write_grants` (conversation, page, mode `suggest | append | replace`, `expires_at`, `revoked_at`). `write_page` refuses unless, in this order: the conversation belongs to the caller, a non-revoked, non-expired grant exists for **that conversation and that page**, the caller passes `require_page_write` **now** (rights changed since the grant, or a grant created on a page the person cannot edit, never help), and the mode allows the operation (`append` refuses `replace`). Creating a grant also requires `require_page_write`.
- `suggest` (the default) writes nothing: the change is stored as an `ai_suggestions` row with a line diff, and applies only when the person accepts it, which re-checks their rights. `append` and `replace` apply directly.
- Every write first saves the current state in `page_revisions` (kind `restore`, label "before AI change"), so any change can be undone from the page history, then writes the Yjs state only if nobody wrote in between (compare-and-swap on `yjs_state`).

## Page format

`pages.content` is only the legacy HTML a page had before it was first opened in the editor. The text of a page lives in `pages.yjs_state` (a ProseMirror document in the `default` XML fragment, edited live through the collaboration server). Agents therefore read and write **Markdown converted to and from that Yjs document** (`ai_pages.rs`, `yrs`), using the same node names as the editor: `mathBlock`/`mathInline` (the LaTeX is the node's text), `mermaid`, `graph` (ADR 0007's line text), `notice` for `:::info` callouts, task lists, tables. The system prompt teaches this syntax. Blocks the converter does not know (boards, embeds, images) are shown as `[bloc non textuel : …]` when reading and are lost by `replace`, which is why a revision is always taken. A page whose text exists only as legacy HTML is converted to Yjs on its first write when it contains only blocks the converter reproduces (paragraphs, headings, lists, quotes, callouts, code, maths, diagrams, marks and links), after a revision of the converted original; otherwise it is refused with `page_not_convertible` rather than converted lossily. Every write also regenerates `pages.content` (HTML) from the new state, since the collaboration server never writes it (browsers push it), so the public page, exports and search see the new text. After a write the backend sends `NOTIFY looty_page_reset`; the collaboration server drops its in-memory copy, refuses to store it over the new state and clients reconnect.

Consequences: the model never gets write power from its prompt or from page content; an expired or revoked grant stops writes immediately; a leaked database dump does not contain usable API keys without `LOOTY_SECRET_KEY` / the secret key file. The cost is friction (one grant per page, per conversation) and a Markdown subset: rich blocks cannot be authored by agents.

## Addendum: study set tools

Agents can also work on study sets (ADR 0009, `docs/study-items.md`) with `create_study_set`, `list_study_sets`, `read_study_set`, `update_study_set` and `read_attempts`, under the same principle: nothing is writable without a grant, and the server uses the rights of the person.

- `ai_study_grants` (conversation, `kind` `create` or `update`, `expires_at`, `revoked_at`). `create` targets one workspace or the personal space; `update` targets one set. `create_study_set` refuses unless the conversation belongs to the caller, a live `create` grant matches the requested workspace (no `workspace_id` means personal space), the caller has docs EDIT in that workspace now, and every item passes `study::validate_item` (strict schema, nothing is created otherwise). The set is **always private** and owned by the caller; sharing stays a human decision. `update_study_set` needs a live `update` grant for that set and edit access from `study::load`; a creation grant never allows it.
- No suggest mode for sets: instead the previous title, kind and items are saved in `study_set_revisions` in the same transaction, and `POST /api/ai/study-revisions/{id}/restore` (edit rights required) puts them back. The chat shows a "restore the previous version" button on each update (the revision id travels in the tool message `data.study_revision_id`), with an undo toast; the study editor lists the same versions.
- Reading uses the person's own access: `list_study_sets` and `read_study_set` go through `study.rs` (`list_for`, `load`); expected answers and explanations are only returned to someone who can edit the set. `read_attempts` filters on the caller's `user_id` in every query, including for the owner of a set, so one person's attempts are never shown to another person's conversation.
- Summary sets (`kind = summary`) reuse the `flashcard` item as a section (`prompt` = heading, `answer.back` = Markdown body), read in a dedicated view with a table of contents; the system prompt teaches this shape.

## Addendum: the Assistant page and authorization cards

The floating panel is replaced by an **Assistant** page in the workspace shell (`/w/{ws}/assistant`, two columns: conversations, thread). The grant model above does not change; only how a person gives a grant does.

- **Cards instead of pickers.** When the model calls `write_page`, `create_study_set` or `update_study_set` and the server refuses with `Forbidden`, `ai_tools::execute` also returns a `grant_needed` card (page or set id, title, workspace; no content) **only if the person could write there themselves** (`require_page_read` + `Write`, docs EDIT, or `study::load` Edit), so a card never offers what the server would refuse. It is streamed as a `grant_needed` event and stored in the tool message `data.grant_needed`, so reloading the conversation shows it again. The card offers the same choices as before (mode `suggest | append | replace` for pages, a duration of 15 min to 24 h) and calls the unchanged grant endpoints; the server revalidates rights on every write, as always. Once a grant is live the card turns into a status with a revoke button. After approving, the page sends the model a short message asking it to retry (the refused call itself is not replayed server-side, so a grant is never created or used behind the person's back).
- **Undo in the thread.** Direct writes (`append`, `replace`) store the page revision taken before the write in the tool message (`data.page_revision_id`); `POST /api/ai/page-revisions/{id}/restore` (page write rights required) puts it back, taking a new revision first so the undo can itself be undone. Accepted suggestions offer the same undo. Study sets keep `study-revisions/{id}/restore`.
- **Attachments, not ambient context.** New conversations have no page context; the person attaches items with `@` or "+" (pages, entraînements, tasks, boards, events, projects), the open item being attached by default and removable. Pages and entraînements are re-read **server-side with the person's rights** when the message is sent (unreadable ones are dropped silently); other kinds travel as a short excerpt supplied by the client, which is the person's own text and grants nothing. The resolved text is stored with the user message (`data.context`) and replayed to the model; the system prompt labels it as context, not instructions.
- **Private, titled conversations.** Conversations stay per user. The model writes a short title after the first exchange (`title_locked` prevents later changes; renaming locks it too) and the list is searched server-side over titles and messages.
