# AI agents are read-only by default and write only through a per-page, expiring grant

People want to ask a model about their pages and have it draft or fix text. The risks are obvious: a model (or an instruction hidden in a page it reads) that rewrites documents nobody pointed it at, reaches pages the person cannot see, or leaks an API key. We considered a global "allow editing" switch, a per-connection permission, and trusting the system prompt; none of them survives a prompt injection, and the first two are too coarse (one page the user wants help on, a whole workspace exposed).

Decision: **a conversation is read-only until the person grants it write access to one exact page, with a mode and an expiry**, and the server enforces everything with the rights of the person, never with what the prompt says.

- `ai_connections` hold the provider (`openai`, `anthropic`, `gemini`, `perplexity`, `openai_compatible` for Ollama and similar), model, optional base URL and the API key **encrypted with `crypto.rs`**. The API never returns the key, only whether there is one and its last four characters. Base URLs follow the CalDAV rules (https and public addresses, unless `CALDAV_ALLOW_PRIVATE` or `AI_ALLOW_PRIVATE` is `true`, which a local Ollama needs).
- Tools offered to the model: `list_pages` and `read_page` (only what `visible_pages` / `require_page_read` give the person, across workspaces including their personal space), and `write_page`.
- `ai_write_grants` (conversation, page, mode `suggest | append | replace`, `expires_at`, `revoked_at`). `write_page` refuses unless, in this order: the conversation belongs to the caller, a non-revoked, non-expired grant exists for **that conversation and that page**, the caller passes `require_page_write` **now** (rights changed since the grant, or a grant created on a page the person cannot edit, never help), and the mode allows the operation (`append` refuses `replace`). Creating a grant also requires `require_page_write`.
- `suggest` (the default) writes nothing: the change is stored as an `ai_suggestions` row with a line diff, and applies only when the person accepts it, which re-checks their rights. `append` and `replace` apply directly.
- Every write first saves the current state in `page_revisions` (kind `restore`, label "before AI change"), so any change can be undone from the page history, then writes the Yjs state only if nobody wrote in between (compare-and-swap on `yjs_state`).

## Page format

`pages.content` is only the legacy HTML a page had before it was first opened in the editor. The text of a page lives in `pages.yjs_state` (a ProseMirror document in the `default` XML fragment, edited live through the collaboration server). Agents therefore read and write **Markdown converted to and from that Yjs document** (`ai_pages.rs`, `yrs`), using the same node names as the editor: `mathBlock`/`mathInline` (the LaTeX is the node's text), `mermaid`, `graph` (ADR 0007's line text), `notice` for `:::info` callouts, task lists, tables. The system prompt teaches this syntax. Blocks the converter does not know (boards, embeds, images) are shown as `[bloc non textuel : …]` when reading and are lost by `replace`, which is why a revision is always taken. A page whose text exists only as legacy HTML is refused with `page_not_opened_in_editor` rather than converted lossily. After a write the backend sends `NOTIFY looty_page_reset`; the collaboration server drops its in-memory copy, refuses to store it over the new state and clients reconnect.

Consequences: the model never gets write power from its prompt or from page content; an expired or revoked grant stops writes immediately; a leaked database dump does not contain usable API keys without `LOOTY_SECRET_KEY` / the secret key file. The cost is friction (one grant per page, per conversation) and a Markdown subset: rich blocks cannot be authored by agents.
