# Android: a second "fdroid" build without self-update, and Looty's own F-Droid repository

GLOSSARY: *Instance de l'app*. Issues 166 and 167 (android 0.30.0), under the parent 139.

F-Droid forbids an app that installs its own updates (downloaded APK, `REQUEST_INSTALL_PACKAGES`) and wants a build from source without proprietary dependencies. Looty's APK updates itself from the download site or GitHub, which stays the default for people who install the APK.

## Decisions

- **Two product flavors** of one module (`distribution` dimension): `direct` (the current app, with the updater) and `fdroid`. The update code (`update/`, the update screen, the install receiver and the two install permissions in a `direct`-only manifest) lives in `src/direct`; `src/fdroid` has a stub `Updater` (only the installed version), a `UpdateWorker` that cancels any scheduled check, and an *App updates* screen that shows the release notes of the latest Android versions (from the instance's `/api/releases`) and says that updates come from F-Droid. Release notes stay in both builds.
- **Same application id and same signing key** for both. The repository's APK is signed by CI with the key already used for the direct APK, so a person can move from one build to the other without uninstalling. The F-Droid main repository signs with its own key: moving between it and the direct APK needs a reinstall, which the documentation says.
- **Unsigned and reproducible**: the `fdroid` build runs with `-Plooty.unsigned` and `SOURCE_DATE_EPOCH`, versions are pinned in Gradle, and the Android workflow builds it twice and fails if the two APKs differ. The repository signs afterwards with `apksigner`.
- **No proprietary dependency**: checked in CI on the runtime classpath (no Play Services, Firebase, ML Kit, Play Store libraries) and the built APK is checked not to ask for the install permissions.
- **Repository on the download site**: `fdroid update` runs in the *F-Droid* workflow after each Android release, with a **repository key distinct from the app key** (a leaked repository key must not allow forging app updates, and the reverse). The index is rebuilt from the latest APK only, so older versions disappear, like `releases/`. The site's upload endpoint now accepts a third top-level folder, `fdroid/`, served at `/fdroid/`. Files are uploaded data first, index last, then stale files are removed.
- **Fingerprint**: published at `/fdroid/fingerprint.txt` and inside the QR code that `fdroid update` generates (`/fdroid/repo/index.png`); the documentation page shows both.
- **Secrets**: `FDROID_KEYSTORE_B64`, `FDROID_KEYSTORE_PASSWORD`, `FDROID_KEY_ALIAS`, `FDROID_KEY_PASSWORD` (new), plus the existing `ANDROID_KEYSTORE_*`, `SITE_UPLOAD_TOKEN` and variable `SITE_URL`. Without them the repository step warns and publishes nothing; a dry run with throwaway keys runs on every Android pull request.
- **Store metadata**: `fastlane/metadata/android/{en-US,fr-FR}` generated by `scripts/fastlane-metadata.mjs` (title, descriptions, changelog of the current version cut to 500 bytes from `backend/releases.json`), checked in CI. Screenshots are not generated and still have to be added by hand under `images/phoneScreenshots/`.

## Consequences

The repository is not the main F-Droid catalogue: submitting to `fdroiddata` is a separate step that needs the screenshots and a metadata merge request. Moving the same build between the direct APK and our repository is seamless; moving to the main catalogue is not.
