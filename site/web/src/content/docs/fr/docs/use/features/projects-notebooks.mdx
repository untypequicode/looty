## Notebooks

- **Moteur d’exécution** : le code s’exécute soit dans votre navigateur (Pyodide, par défaut), soit sur le **serveur Jupyter** du projet. Le choix est enregistré dans le notebook et vaut pour tout le monde ; chaque personne a son propre noyau, les sorties sont partagées.
- **Dépendances du projet** : les bibliothèques sont listées dans `requirements.txt` à la racine du projet et installées par chaque noyau Pyodide à son démarrage. Une bibliothèque n’y entre que par un geste explicite (bouton *Installer*, `%pip install`, ou modification du fichier).
- **Modules du projet** : un fichier Python du projet qu’une cellule peut importer par son nom.
- **Serveur Jupyter** : une personne qui peut modifier le projet déclare un serveur externe (adresse, jeton, noyau par défaut). Seul le serveur Looty le contacte et le jeton n’est jamais montré. L’administrateur de l’instance doit autoriser les réseaux privés si besoin (`JUPYTER_ALLOW_PRIVATE`, voir [Jupyter côté hébergement](/fr/docs/host/services/)).
- **Lien public** : les visiteurs voient le notebook tel qu’enregistré, sans pouvoir l’exécuter.
- **Barre d’outils de texte** : pendant l’édition d’une cellule de texte, des boutons insèrent du gras, de l’italique, un lien, une image, une formule ou une liste à puces autour de la sélection.
- **Export** : le menu *Exporter* enregistre le notebook en page web (`.html`), en PDF (par la fenêtre d’impression du navigateur), en script Python (`.py`, un bloc `# %%` par cellule) ou en `.ipynb` autonome dont les images du projet sont jointes à leurs cellules. Les sorties sont celles affichées à l’écran.
- **Complétion du code** : dans une cellule de code, des suggestions apparaissent en tapant (ou avec Ctrl+Espace). Avec Pyodide elles viennent de Jedi, une fois Python démarré ; avec un serveur Jupyter, du noyau lui-même, à travers le serveur Looty.

## R, R Markdown et Quarto

- **Notebooks R, dans le navigateur, sans rien installer** : dans la fenêtre *Moteur*, choisissez **R (navigateur)**. R s’exécute dans votre navigateur avec [WebR](https://docs.r-wasm.org/webr/latest/) (R compilé en WebAssembly), comme Python avec Pyodide : ni serveur, ni Jupyter, ni installation. Le choix est enregistré dans le notebook (`kernelspec` `ir`, langage R) : il s’ouvre donc aussi dans JupyterLab. Chaque personne a sa propre session R et les sorties sont partagées, comme pour Python. Les cellules ont la coloration syntaxique R et la complétion (R de base et paquets chargés) ; texte, messages, avertissements, erreurs, data frames (tableaux HTML) et graphiques (PNG) s’affichent. Le moteur est servi par Looty lui-même (aucun CDN tiers, donc compatible avec les instances auto-hébergées et hors ligne) et n’est téléchargé que lorsqu’un notebook exécute du R pour la première fois : environ 30 Mo la première fois, puis conservé par le navigateur. L’installation de paquets fait exception : `install.packages("x")` ou `webr::install("x")` dans une cellule télécharge des versions WebAssembly depuis le dépôt public WebR (`repo.r-wasm.org`), seulement quand votre code le demande. Pour installer des paquets à chaque démarrage, listez-les (un par ligne, `#` pour les commentaires) dans un fichier du projet nommé `r-packages.txt` ; l’ajout y est manuel, contrairement à `requirements.txt` pour Python.
  - **Limites de WebR** : un calcul en cours ne peut pas être interrompu, seulement arrêté par *Redémarrer R* (la session R est perdue) ; pas encore de graphiques SVG (PNG seulement) ; seuls existent les paquets compilés pour WebAssembly (la plupart des paquets en R pur et beaucoup de paquets compilés courants) ; les fichiers écrits par R restent dans la session du navigateur, lisez les fichiers du projet (`read.csv("data.csv")`) directement ; la mémoire est limitée par le navigateur.
- **Notebooks R sur un serveur Jupyter** : sinon, choisissez le serveur Jupyter du projet et un noyau R (IRkernel, souvent `ir`) dans la fenêtre *Moteur* : tous les paquets de cette machine, vraie interruption, graphiques SVG, complétion du noyau. Le moteur Python (Pyodide) n’exécute pas de R : une cellule R lancée avec lui affiche un message explicite, rien n’est exécuté comme du Python.
- **Documents R Markdown et Quarto** : dans l’arborescence (ou le menu du projet quand le fichier est ouvert), *Ouvrir comme notebook* convertit un fichier `.Rmd` ou `.qmd` en un nouveau `.ipynb` à côté, réglé sur le moteur *R (navigateur)* (modifiable dans la fenêtre *Moteur*). L’en-tête YAML devient une cellule brute, le texte des cellules Markdown, les chunks ```` ```{r} ```` des cellules de code qui gardent leur en-tête exact (`echo=FALSE`, `fig.width=6`, lignes `#|` de Quarto). Les chunks d’un autre moteur (bash, sql…) deviennent des cellules brutes jamais exécutées. La conversion est sans perte : *Exporter* propose `.Rmd` et `.qmd` et le document revient tel qu’il était (les sorties ne sont pas écrites dans ces fichiers).
- **Rendu** : les exports HTML et PDF respectent `echo=FALSE`, `include=FALSE`, `results="hide"` et les lignes Quarto `#| echo: false`, et omettent l’en-tête YAML.
- **Panneaux R** : sur un notebook R exécuté dans le navigateur (WebR) ou par un serveur Jupyter, le bouton de panneau de la barre d’outils ouvre quatre onglets. *Environnement* liste les variables de la session (nom, type, taille ; cliquez un data frame pour voir ses premières lignes) et s’actualise après chaque calcul. *Graphiques* garde dans l’ordre ceux des cellules et de la console, avec export PNG et SVG (SVG quand le noyau en envoie un). *Aide* affiche la documentation d’une fonction (`mean`, `stats::lm`, ou `?mean` dans la console). *Console* exécute du R sur le même noyau que les cellules. Ces requêtes sont silencieuses : elles ne créent jamais de cellule ni de numéro d’exécution. Ctrl+Maj+Entrée exécute le chunk, Ctrl+Alt+Entrée envoie la ligne ou la sélection à la console. Une requête demande le droit de modifier et un noyau connecté ; un long calcul retarde la réponse.

## Utiliser son propre PC comme serveur Jupyter

Quand l'administrateur a activé les tunnels PC (`LOOTY_TUNNELS=on`), une personne qui peut modifier un projet exécute ses notebooks sur **son propre ordinateur**, sans port ouvert ni réglage du routeur : un petit agent (`looty-bridge`) sur le PC ouvre une connexion sortante vers l'instance, tant qu'il tourne.

1. Dans le notebook, ouvrez la fenêtre **Moteur**, choisissez **Serveur Jupyter**, puis **Utiliser mon PC**.
2. Choisissez le service (Jupyter avec Python, R ou d'autres noyaux) et l'adresse de Jupyter sur votre PC (`http://127.0.0.1:8888` par défaut), lisez l'avertissement et cochez la confirmation. Looty crée le **jeton de tunnel** et l'affiche **une seule fois**, avec la ligne à lancer sur le PC et l'adresse de l'instance déjà remplie : `nix run`, Docker Compose (`docker-compose.bridge.yml`) ou le binaire téléchargé. Le jeton ne s'affiche plus ensuite : révoquez le tunnel et créez-en un autre si vous le perdez.
3. La fenêtre montre le statut en direct : en attente de l'agent, connecté (machine, latence) ou déconnecté. Les noyaux de votre Jupyter sont listés comme ceux de n'importe quel serveur Jupyter.
4. **Déconnecter et révoquer** coupe la connexion immédiatement. Tous vos tunnels sont listés, avec un bouton de révocation, dans **Paramètres, Tunnels PC**.

Si le PC se déconnecte, les notebooks affichent un message clair et rien n'est redirigé en silence : relancez l'agent, ou passez le notebook sur le moteur du navigateur (Pyodide ou R) en attendant.

**Sécurité** : connecter un Jupyter à un projet permet à toute personne qui peut modifier ce projet d'exécuter du code sur votre PC, avec les droits de votre utilisateur, chacune dans son propre noyau. Il n'y a pas encore de restriction par personne : rattachez le tunnel à un projet que vous seul pouvez modifier (par exemple dans votre espace personnel), lancez l'agent avec un utilisateur sans privilèges, idéalement dans un conteneur, et gardez le jeton propre à Jupyter activé. La fonction est masquée quand `LOOTY_TUNNELS` n'est pas `on` et indisponible dans la démo.
